Handover · Power BI implementation

Putting the parts classification into Power BI

22 September 2026 · for the meeting of 23 September · the classification file is ISZE_Parts_Classification_for_PBI_20260922.csv, 164,904 rows, one row per part number

What this is, in one paragraph

A single file, one row per part number, giving every part a place in one three-level family tree. Load it into Power BI as a dimension table, join it to the sales or order fact table on the part number, and the existing pages can be cut by part family without any new measures.

The three levels are one tree, not three views. Level 1 is the family, level 2 the group inside it, level 3 the specific type. Every part has exactly one path, and the same path applies to every market — there is no country or customer column in the file, so there is nothing to disagree about between markets. That is the point of it.

The one decision to make in the meeting

Our own working file currently carries two competing level-1 vocabularies — a 23-value one and a 7-value one — and they agree on 0% of rows. This handover file resolves that by shipping one tree. Whoever builds must not load both, or you get exactly the confusion you are trying to remove.

The implementation, step by step

1

Load the file as a dimension table

Get Data → Text/CSV → the file → Transform Data, not Load. In Power Query:

  • Set the data type of part_key to Text, not Whole Number.
  • Set is_part to True/False.
  • Rename the query to Parts Classification. Do not call it “AIM” or a market name. It is not market-specific.
Do not skip this

If part_key loads as a number, Power BI will silently drop the leading zeros and the join will fail on every part number that starts with 0. That is several thousand parts. Type it as Text in Power Query before it reaches the model.

2

Build the matching key on the fact table

The fact table holds the material number in whatever format the source gives. Add a calculated column there, not in the dimension, so the dimension stays a clean lookup:

Part Key =
VAR Raw = TRIM ( 'Fact'[MATERIAL] )
VAR Padded = REPT ( "0", 10 - LEN ( Raw ) ) & Raw
RETURN
    RIGHT ( Padded, 10 )

The RIGHT(…, 10) matters. Some source rows already run past ten characters; without it the padding produces a key of the wrong length and those rows fall out of the join silently.

3

Relate the two tables

Model view → drag part_key onto Part Key. Then:

  • Cardinality: one to many (one classification row to many fact rows).
  • Cross-filter direction: single. Not both. Both creates ambiguity and Power BI will mark the relationship as inactive.
  • Mark it as active if it is the only join on this key.

Check the model view afterwards: the relationship line must be solid, not dotted. A dotted line means Power BI has deactivated it.

4

Hide what should not be in the field list

Right-click and Hide in report view on: part_key, and the three legacy_aim_* columns. Leave level_1, level_2, level_3, is_part, not_part_type and brand_programme visible.

5

Order the levels so they sort sensibly

Power BI sorts text alphabetically, which puts “Transmission” between “Steering” and “Wheels”. To control it, in the dimension table create Sort by column pairs:

  • Add a level_1_order column (1 to 18, by value descending) and set level_1 to sort by it.
  • Do the same for level_2 and level_3 if the axes come out jumbled.
6

Add the two flags as slicers, and default them

On any page where the classification appears:

  • is_part → slicer or page filter, defaulted to TRUE. Lubricants, logistics and literature then stay out of a parts view unless someone asks for them.
  • brand_programme → slicer. This is what lets Shell be read on its own.

Add “Unclassified” as a visible value, not a filter-out. It has to stay on the page so the review queue stays honest.

Lubricants: yes, separate them — and Shell separately again

You asked whether to split Shell out. The data says yes, and cleanly.

Lubricants and chemicals are 2.0% of the book at €371,237, across 91 part numbers. Of that, the Shell range is €258,522 on seven part numbers. And the fourth-largest single line in the whole order book is one lubricant: 0550047337, engine oil, at €187,849.

So a lubricant is not a rounding error in a parts table. It is big enough to top a page, which is exactly why it should not be allowed to.

The rule that catches Shell

Shell lubricants sit on the 5500* part-number range. There is one trap in it, and it caught me while building this file:

-- WRONG: after padding to 10 digits, every part becomes 0-prefixed
-- 0550047337 starts with "0550", so this matches nothing
LEFT ( [part_key], 4 ) = "5500"

-- RIGHT: test the SHORT form, the way the rule is actually written
LEFT ( TRIM ( [part_key] ), 4 ) = "5500"

In Power Query this is the same idea, on the un-padded value:

Is Shell = Text.StartsWith ( Text.Trim ( [MATERIAL] ), "5500" )

And the design decision: do not make Shell a family. Make it a second dimension so the two questions stay separable:

Family (level 1)

Lubricants & Chemicals — one family, so “how big is our non-parts business” has a single answer.

Brand programme (attribute)

Shell vs Isuzu or other — so Shell can be sliced out of it in one click, without a fourth level.

This way the family tree stays clean and three levels deep, and the Shell question is answered by a filter. If you put Shell in as a family instead, you break the tree: Shell oil is a lubricant, and it would be both.

The same flag marks what the classification deliberately leaves out. In the file, is_part = FALSE covers lubricants, logistics and literature — and separately, the 4,933 rows in the review queue keep their Unclassified label rather than being forced into a family that isn't right.

Engines and cabs

These are the two you asked about, and they behave very differently. I would not give either one its own family.

Engines: already a family, and the interesting part is what happens to a whole engine

Engine is a level-1 family at €564,497 in the period. Two things about it are worth knowing:

The engine business is dominated by a handful of very expensive parts. The single largest is a partial engine at €86,020 — six pieces at €14,337 each. The second is €28,392 for two pieces at €14,196 each. In a family where the average piece is worth €9.90, one part can move the whole month.

That is an argument for reading engines at level 3, not level 1. At level 1 a single engine swap looks like a trend in the engine business.

And there is a clean-up to agree before he builds. Our existing tree has a leaf called “Lubrication” which contains no lubricant at all — it holds drain-plug gaskets, drain plugs and oil-cooler cores. Oil-system hardware, not oil. In the file I built for him I folded it into Engine, because that is what it physically is. If he disagrees, it is a one-line change; but it should not stay labelled “Lubrication” next to a genuine lubricant family, or the two will be confused forever.

Cabs: not a family, and for a good reason

There is no cab family today, and I would not add one. Here is why, and he should hear it in these terms.

Cab content is €509,375 across 988 part numbers, but it is 97% structure and trim, not a product line. Look where it actually sits:

What “cab” content really is, by the family it belongs in

If you make a cab family, then a blower unit belongs to both Cabin Air and Cab, a seat belongs to both Cabin Interior and Cab, and a cab mount belongs to both Chassis and Cab. You get a part in two families and a double count the first time anyone adds a column up — which is precisely the defect his own catalogue tree has today, where one section name appears under several headings.

What he actually needs is one thing, and it is much smaller than a family: the nine cab-assembly part numbers at €66,679. A complete cab shell is a different commercial animal from a cab mount. So add a flag, not a family:

-- one flag, no new level
is_major_assembly = TRUE for a cab assembly, and later for engine,
                    transmission and axle assemblies

Then “are we selling whole assemblies or only repair parts” is a filter, and nothing is counted twice. This is the general rule I would give him: if a value is a property of a part rather than a place to put it, make it a flag. Families partition; flags annotate. Mix the two and the tree stops reconciling.

What I would say to him, in order

  1. It is one tree, and it is already the same for every market. Three levels, one parent chain, no country dimension. Nothing to reconcile between countries.
  2. It is a dimension table, joined on the part number. No new measures, no new logic in the existing pages — the pages keep their numbers and gain a family slicer.
  3. Start on MASTER DATA, because it is already a part-number table. Then ORDER, then the fill-rate pages.
  4. Parts and non-parts are separated in the data, not by convention. Lubricants, logistics and literature carry is_part = FALSE, and Shell is a brand attribute on top of that.
  5. Engines and cabs are not new families. Engines already is one and should be read at level 3; a cab shell is an assembly flag, not a family, or you double count.
  6. Two things are deliberately not in this file and he should know: Isuzu Genuine versus BVP, and covered by that, whether we can say anything about value-parts mix on the same page. Both are available; they are a second and third column and I can add them.
  7. The one decision that is his: confirm the renamed level 1 as the standard, so the old vocabulary gets retired rather than run alongside.
