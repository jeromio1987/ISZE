## What's genuinely good, well executed

**The monitoring layer.** You've built seven recurring scheduled tasks — dashboard freshness, UIO staleness, tender-scraper healthcheck, pricing basket monitor, AIM classification refresh, weekly intelligence brief, memory review. That's turning "is my data actually trustworthy" from a manual worry into a standing weekly check. Most people doing pricing/UIO/PMS analysis at this level don't build this; they find out their numbers were stale when someone in a meeting asks the wrong question. This is real infrastructure, not busywork.

**Your quality control instinct is sharp and it catches real things, not cosmetic ones.** Two examples from the last month:
- On the GPS-through-2030 model, you rejected a simplified redesign because the per-DB growth-driver breakdown (UIO growth vs. target lift) had quietly disappeared, and you insisted the CIS distributors with no UIO data still be shown explicitly — correctly pointing out that otherwise the total Kosha target math doesn't reconcile. That's not a formatting complaint, that's catching a broken methodology before it went into a document.
- On the dashboard freshness report, you correctly overrode the "urgent — 113 days old" flag on Sales CY25.XLSX because it's a closed calendar year, not a live feed. Ten seconds of pushback, correct call, and it stopped a false alarm from propagating into next week's report.

**The written "honest internal framing" in your memory** — Kosha being structurally unreachable, ISZE having no real FX discretion — is the right instinct. It's unambiguous and it'll hold up if someone challenges it later, instead of being reconstructed under pressure in the moment.

## Where it's costing you efficiency

**File and version sprawl is a standing tax, not a one-off problem.** In the sessions I read, drift showed up repeatedly: the PRISM UIO copy sat 6 days behind canonical; `hub/index.html` was quietly serving an old embedded AIM snapshot instead of linking to the live dashboard; 8 separate deploy-mirror files needed manual patching to remove a stale "0.3%" PMS figure; a 674k-row unclassified price file (`Price file 2026_full.xlsx`) has been sitting next to the 164k-row classified canonical file for weeks with nobody confirming which one is authoritative. None of these individually is a big deal. Together, they mean every analysis has to start with "which copy is actually current" instead of just trusting the number. A build/publish script that regenerates deploy mirrors and derived copies from a single canonical source — instead of hand-patching each one when caught — would remove this permanently instead of catching it after the fact, weekly, forever.

**Your memory systems disagree with each other, and that's a real risk, not a tidiness issue.** One weekly "memory review" run deleted the lubricants project file as stale/inactive. The same week, a separate session found IML had actually signed off lubricants as live back on 8 May, with real revenue (~€37K net FY2025) and one concrete blocker. Your global CLAUDE.md — injected into every session you run — still says lubricants is "Awaiting IML go-ahead," which is now simply wrong. This isn't a one-time slip; it's what happens when the same fact lives in three places (CLAUDE.md, `ISZE/05_memory/`, the `isze-context` skill) with no single owner keeping them in sync. Worth deciding which one is the actual source of truth and having the other two defer to it — otherwise a future session will confidently act on the wrong status.

**Detection is strong; closing the loop is the weak point.** The tender scraper's 6-week outage was root-caused twice, in two separate weekly runs, down to a specific 2-line Task Scheduler patch — and as of the last check it still hadn't been applied, because the last step needs a manual re-import on your machine. Same pattern elsewhere: you told the dashboard freshness check to "skip" the ITUK PMS Analysis file, which currently exists only in an `_archive` folder and is 91 days old — while the ITUK PMS pilot is listed as actively running. Skipping it once is fine; skipping it across multiple weekly runs without a decision means the pilot may be working off stale analysis without anyone deciding that's acceptable. The gap isn't the thinking, it's that flagged fixes need someone to actually do the 2-minute physical step, and right now they're piling up unresolved.

**Skill files go stale silently.** The `isze-context` skill was found to still cite a superseded 0.3% PMS capture figure and an "ITUK dispute" framing that's since resolved to "manageable" — meaning any session that leans on that skill for context starts from outdated facts unless someone happens to catch it, as happened here almost by accident during a UTI deck build. Worth a periodic "does this skill still match reality" pass, same as you already do for dashboards and data.

**A specific near-miss worth flagging on its own:** the AIM classification refresh found two different "87%" figures in your systems that mean opposite things — one is AIM classification coverage (higher is good), the other is a GPS dashboard's unclassified-revenue metric (higher is bad) — sourced from different systems, three weeks apart, with matching digits by coincidence or by mix-up, unconfirmed which. That's exactly the kind of number that looks fine in a spreadsheet and only breaks in a live meeting when someone asks a follow-up question. It's flagged in your own `DATA_INTEGRITY_FLAGS` doc but hasn't been reconciled yet.

## Mixed bag, not clearly good or bad

Four of your monitoring tasks (dashboard freshness, UIO staleness, memory review, tender-scraper healthcheck) run on overlapping weekly cycles and substantially re-check the same folders. That's thorough, but if the separate reports aren't each producing a distinct action, some of that could probably merge into one weekly pass without losing coverage.

## Bottom line, honestly

Nothing here is a bad idea in the sense of "shouldn't have done that." The instincts are good — you catch wrong numbers before they go external, you push back correctly when something's been oversimplified, and the automated-monitoring approach to ISZE data is the right call for the scale of decisions riding on it. The actual gap, consistently, is closing loops: patches proposed and not applied, paths marked "skip" and left unresolved across multiple runs, memory sources quietly diverging from each other. That's the predictable cost of running a lot of automated infrastructure without a short recurring pass to clear what it's found. Given how well the detection side already works, that's a fixable operational gap, not a capability problem.

One meta-point, since this "give me feedback" task itself appears to run on a recurring schedule: the substance here doesn't change week to week as fast as the check runs. Worth considering whether this should be quarterly, or whether what you actually want week to week is a running list of open loops (unapplied patches, unresolved path flags, memory contradictions) rather than a fresh personality assessment each time.
